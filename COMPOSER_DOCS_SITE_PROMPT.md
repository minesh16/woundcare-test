## Part B — Cursor Hooks for staying current

Set up `.cursor/hooks.json` plus supporting scripts in `.cursor/hooks/`. Requirements:

1. **Trigger:** an `afterShellExecution` hook with a `matcher` on git commit commands (e.g. matching `^git commit`), so it fires right after a commit is made **through a shell Cursor can see** (its integrated terminal or the agent's own shell tool).
   - **Known limitation — document this explicitly in the Contributing/docs-automation page:** Cursor Hooks have no native "on git commit" event. This approach only catches commits run through a Cursor-visible shell. It will **not** fire for a commit made in a fully external terminal window or another editor. As a lightweight backstop for that case, also add a plain **git `post-commit` hook** (`.git/hooks/post-commit`, or via a tool like `simple-git-hooks` since this is already a Node project) that just prints a reminder to stdout ("source files changed — run the docs-check in Cursor / re-open Composer to refresh docs-site") — no AI call, just a nudge, since it can't invoke Composer directly from a raw git hook.
2. **Behavior when it fires:**
   - Diff the commit (`git show --name-only HEAD` or equivalent) to see which files changed.
   - Maintain an explicit mapping (as a small config/table you create, e.g. `.cursor/hooks/doc-map.json`) from source paths to the docs-site pages that describe them (e.g. `src/decision/**` and `src/decision/engine.ts` specifically → `.../architecture/decision-engine.md`; `src/cv/**`, `src/assessment/**`, `api/**`, `api/v1/assessments/**` → `.../architecture/pipeline.md`; `src/copy/**` → the plain-language/presentation section; `supabase/migrations/**` and `supabase/README.md` → the data/persistence section of `operational-status.md`; `docs/HANDOFF.md` (status/gaps sections specifically) → `.../roadmap.md` and `.../operational-status.md`; `app.json`/`package.json` → `.../platforms.md` and `.../tech-stack.md`). Keep this map current as the repo grows — it's the thing most likely to silently go stale, so give it its own entry on the Contributing/docs-automation page telling future contributors to extend it when they add a new top-level module.
   - For any changed path that maps to a doc page, **draft an updated version of that page as an uncommitted working-tree edit** (do not auto-commit, do not auto-push — the user reviews and commits it themselves like any other change).
   - When editing, **merge/update rather than blindly overwrite** — preserve any hand-written prose, callouts, or `<!-- Unverified -->` notes that aren't contradicted by the actual code change.
   - Stamp each auto-touched page with a trailing HTML comment marker, e.g. `<!-- docs-hook: last auto-checked against commit <short-sha> on <date> -->`, so it's obvious which pages were machine-touched and when.
   - Log every run (files changed, pages touched, pages skipped and why) to `.cursor/hooks/doc-update.log` for auditability.
   - Message the user (via the hook's `user_message`) summarizing what it updated so it's visible in the Cursor UI, not silent.
3. **Guardrails:**
   - Never edit anything outside `docs-site/` from this hook.
   - Never touch `.env`, secrets, or credentials, and never write real secret values into any doc page even if referenced in code comments.
   - If `docs-site/` doesn't exist yet (e.g. hook fires before Part A is done), no-op safely.
   - Keep `loop_limit` conservative and `failClosed: false` (a hook failure should never block a commit).
